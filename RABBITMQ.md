## 1. Протокол AMQP 0-9-1 и архитектура RabbitMQ

RabbitMQ работает по протоколу **AMQP 0-9-1** (Advanced Message Queuing Protocol). В отличие от HTTP, который является синхронным протоколом типа "запрос-ответ" поверх короткоживущих TCP-соединений, AMQP спроектирован для асинхронного полнодуплексного обмена сообщениями поверх долгоживущих соединений.

### 1.1 Architectural Blueprint: From Thread/Worker to Queue

```text
+------------------------------------------------------------------------------------+
|                                 CLIENT APPLICATION                                 |
|                                                                                    |
|  +---------------------+    +---------------------+    +---------------------+     |
|  |   Thread/Worker A   |    |   Thread/Worker B   |    |   Thread/Worker C   |     |
|  |  (Handles HTTP Req) |    |  (Handles Cron Job) |    | (Handles Analytics) |     |
|  +----------│----------+    +----------│----------+    +----------│----------+     |
+─────────────┼──────────────────────────┼──────────────────────────┼────────────────+
              │                          │                          │
              ▼ (Channel 1)              ▼ (Channel 2)              ▼ (Channel 3)
        ┌───────────┐              ┌───────────┐              ┌───────────┐
        │  Frame 1  │              │  Frame 2  │              │  Frame 3  │ (AMQP Frames)
        └─────┬─────┘              └─────┬─────┘              └─────┬─────┘
              │                          │                          │
              └──────────────────────────┼──────────────────────────┘
                                         ▼ (Multiplexing inside Client library)
======================================================================================
[                     SINGLE PHYSICAL TCP CONNECTION (Port 5672)                     ]
======================================================================================
                                         │
                                         ▼ (Demultiplexing inside RabbitMQ Broker)
+------------------------------------------------------------------------------------+
|                                  RABBITMQ BROKER                                   |
|                                                                                    |
|             ┌───────────────┐                      ┌───────────────┐               |
|             │  Exchange 1   │                      │  Exchange 2   │               |
|             │ (Direct/Topic)│                      │   (Fanout)    │               |
|             └───────┬───────┘                      └───────┬───────┘               |
|                     │ (Bindings via Routing Keys)          │ (Broadcasts to all)   |
|             ┌───────┴───────┐                      ┌───────┴───────┐               |
|             ▼               ▼                      ▼               ▼               |
|       [  Queue A  ]   [  Queue B  ]          [  Queue C  ]   [  Queue D  ]         |
|             │               │                      │               │               |
|             ▼               ▼                      ▼               ▼               |
|        Consumer A      Consumer B             Consumer C      Consumer D           |
+------------------------------------------------------------------------------------+
```

### 1.2 Glossary of Core Terms

- **Thread / Worker:**
  Это параллельные единицы выполнения в твоем бэкенде. В многопоточных языках (например, Java или Go) это реальные потоки ОС или горутины. В Node.js, несмотря на работу в одном основном потоке (Event Loop), это параллельно выполняющиеся асинхронные задачи (Promises/Callbacks) или отдельные дочерние потоки `Worker Threads`.
  - _Почему их несколько?_ Потому что сервер обрабатывает несколько задач одновременно: Воркер А обрабатывает HTTP-запрос пользователя на бронирование, а Воркер Б в этот же момент выполняет фоновую крон-задачу по очистке старых сессий.
- **Channel:**
  Легковесное виртуальное соединение внутри физического TCP-соединения.
  - _Зачем нужно несколько каналов?_ Потому что кадры (frames) протокола AMQP не являются потокобезопасными. Если бы Воркер А и Воркер Б попытались писать свои сырые байты в _один и тот же канал_ в одну и ту же миллисекунду, данные перемешались бы и повредились, из-за чего RabbitMQ разорвал бы всё соединение. Выделяя `Channel 1` для Воркера А и `Channel 2` для Воркера Б, клиентская библиотека может безопасно объединять (мультиплексировать) их фреймы в одну физическую TCP-трубу.
- **TCP Connection:**
  Реальное физическое сетевое соединение (сокет), установленное между подом твоего приложения и подом RabbitMQ. Оно держится открытым постоянно, чтобы избежать огромных накладных расходов на создание новых TCP-соединений при каждой отправке сообщения.
- **Exchange:**
  Маршрутизатор сообщений. Он принимает сообщения из каналов и распределяет их по очередям на основе ключа маршрутизации (Routing Key) и правил привязки (Bindings).
- **Routing Key:**
  "Адресная метка", написанная на конверте сообщения.
- **Queue:**
  Почтовый ящик, в котором хранятся сообщения, пока их не заберет получатель.
- **Consumer:**
  Код получателя (в нашем случае это методы с декоратором `@RabbitSubscribe` или `@RabbitRPC` внутри классов `*.consumer.ts`), который ожидает и обрабатывает сообщения из конкретной очереди.

## 2. Анатомия обмена (Exchanges) и роль Очередей (Queues) через аналогию Почты

Чтобы понять, как сообщения ходят внутри RabbitMQ, давай на время забудем про код и представим обычную **Почтовую службу**.

### 2.1 Разбор ролей: Кто есть кто?

1.  **Продюсер (Отправитель):** Вы написали письмо. Вы не знаете, кто именно его прочитает и где этот человек живет. Ваша задача — написать адрес на конверте (**Routing Key**) и бросить письмо в сортировочное окно (**Exchange**).
2.  **Exchange (Сортировщик):** Это умный робот в почтовом отделении. Он берет ваш конверт, смотрит на адрес (**Routing Key**) и решает, в какие почтовые ящики (**Queues**) нужно разложить копии этого письма.
3.  **Queue (Почтовый ящик):** Это ящик на стене. Письма лежат в нем и копятся, пока за ними кто-то не придет. **Очередь — это буфер хранения.**
4.  **Consumer (Получатель):** Это человек (наш код консьюмера), который открывает ящик, достает письма и обрабатывает их.

---

### 2.2 Где вступает в роль Очередь (Queue), когда слушателей много?

Когда у нас запущено несколько копий микросервисов (слушателей), распределение сообщений зависит от того, к каким **ящикам (очередям)** они подключены:

#### Сценарий А: Много слушателей подключены к ОДНОМУ ящику (Очереди)

_Аналогия: Один почтовый ящик `auth-queue`, у которого стоят 3 почтальона (консьюмера)._

```text
               ┌───────────┐
               │  Очередь  │  --> [Сообщение 1] [Сообщение 2] [Сообщение 3]
               └─────┬─────┘
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
  [Воркер 1]    [Воркер 2]    [Воркер 3]
 (Сообщение 1) (Сообщение 2) (Сообщение 3)
```

- **Как это работает:** Сообщения лежат в одной очереди. RabbitMQ отдает Сообщение 1 -> Воркеру 1, Сообщение 2 -> Воркеру 2, Сообщение 3 -> Воркеру 3.
- **Итог:** **Каждое сообщение обрабатывается только ОДНИМ воркером.** Они не дублируются.
- **Зачем нужно:** Для масштабирования производительности (Load Balancing). Чем больше воркеров слушают одну очередь, тем быстрее разгребается завал писем.

#### Сценарий Б: Слушатели подключены к РАЗНЫМ ящикам (Очередям)

_Аналогия: Два разных ящика на стене: `billing-queue` и `notifications-queue`._

```text
                          ┌──────────────┐
                          │   Exchange   │
                          └──────┬───────┘
                                 │ (Копирование сообщения)
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
       ┌──────────────────┐             ┌──────────────────┐
       │ Очередь Billing  │             │ Очередь Notif    │
       └────────┬─────────┘             └────────┬─────────┘
                ▼                                ▼
       [Сервис Платежей]                [Сервис Уведомлений]
      (Копия сообщения)                 (Копия сообщения)
```

- **Как это работает:** Exchange получает сообщение и видит, что его Routing Key совпадает с правилами привязки обоих ящиков. Он **копирует** сообщение и кладет по копии в каждый ящик.
- **Итог:** **Оба сервиса получают полную копию сообщения.**
- **Зачем нужно:** Для уведомления разных независимых систем (микросервисов) об одном событии (Publish/Subscribe).

---

### 2.3 Зачем нужно несколько разных Exchanges (Сортировщиков)?

В одном почтовом отделении может стоять несколько разных роботов-сортировщиков (Exchanges), потому что они работают по абсолютно разным правилам (алгоритмам):

#### Робот 1: Direct Exchange (Педант)

- «Кладу письмо в ящик только в том случае, если адрес на конверте **символ-в-символ** совпадает с правилом привязки ящика».
- _Пример:_ На конверте написано `auth.login` -> письмо летит строго в ящик `auth.login`.

#### Робот 2: Fanout Exchange (Расклейщик объявлений)

- «Мне плевать, какой адрес написан на конверте. Я делаю копию этого письма и кидаю абсолютно во все почтовые ящики, которые ко мне подключены».
- _Пример:_ Уведомление о технических работах рассылается во все очереди.

#### Робот 3: Topic Exchange (Тематический сортировщик)

- «Я умею читать маски и шаблоны адресов с использованием звездочек `*` и решеток `#`».
- _Пример:_ Если на ящике написано `*.orders.#`, робот положит туда письма с адресами `eu.orders.created`, `us.orders.failed` и т.д.

## 3. Паттерны консьюмеров: @RabbitSubscribe (В одну сторону) vs @RabbitRPC (С ответом)

С точки зрения **слушателя (получателя)** сообщений, в NestJS есть два типа обработчиков:

### 3.1 @RabbitSubscribe — Односторонний консьюмер (Fire and Forget)

Используется, когда от получателя **не требуется отправлять никакого ответа** обратно отправителю.

- **Принцип работы консьюмера:** Метод принимает сообщение, выполняет какую-то работу (например, отправляет Email или сохраняет логи) и завершается. Функция ничего не возвращает (`void`).
- **Аналогия (ты — получатель):** Тебе в ящик бросили открытку: _«Я купил машину!»_. Ты её прочитал, порадовался за друга и пошёл по своим делам. **Тебе не нужно писать никакого ответа.**

### 3.2 @RabbitRPC — Двусторонний консьюмер (Remote Procedure Call)

Используется, когда отправителю **обязательно нужен результат** твоих вычислений.

- **Принцип работы консьюмера:** Твой метод обрабатывает входящие данные (например, валидирует JWT-токен пользователя) и **обязательно возвращает результат** через `return user`. Библиотека под капотом автоматически перехватит этот `return` и отправит его обратно в RabbitMQ, который доставит его конкретно тому сервису, который сделал запрос.
- **Аналогия (ты — справочная служба):** Тебе в ящик кинули письмо с вопросом: _«Какая сегодня погода в Берлине?»_. Ты не можешь просто прочитать его и проигнорировать. Твоя прямая обязанность — узнать погоду и **обязательно отправить ответное письмо** с текстом _«Сегодня +20»_ обратно отправителю.

## 4. Подтверждения сообщений: ACK, NACK и Requeue

0

Когда консьюмер забирает сообщение из очереди, оно переходит в статус `Unacknowledged` (ожидающее подтверждения). RabbitMQ должен понять, успешно ли обработано сообщение, чтобы решить его судьбу.

- **ACK (Acknowledge):** Подтверждение успеха. Консьюмер сообщает: _«Я успешно обработал сообщение. Удали его из очереди»_. Сообщение уничтожается в брокере.
- **NACK (Negative Acknowledge):** Сообщение об ошибке. Консьюмер сообщает: _«Произошла ошибка при обработке»_.
  При отправке NACK консьюмер указывает флаг `requeue`:
  - `requeue: true` — RabbitMQ возвращает сообщение обратно в очередь. Оно будет доставлено повторно этому же или другому воркеру.
  - `requeue: false` — сообщение удаляется из очереди без возврата. И именно здесь включается механизм **DLX**.

## 5. Обработка ошибок и Dead Letter Exchange (DLX / DLQ)

Если при обработке сообщения произошла критическая или неисправимая ошибка (например, неверный формат данных), возвращать его в очередь через `requeue: true` бессмысленно — оно будет бесконечно падать и грузить систему.

Для спасения таких сообщений используется **Dead Letter Exchange (DLX)** — обменник «мертвых» писем.

### 5.1 Схема работы "Мертвых писем"

1.  Очередь создается с настройкой `x-dead-letter-exchange`, указывающей на специальный `DLX-обменник`.
2.  Если консьюмер отвечает **NACK** с флагом `requeue: false` (или у сообщения истекает время жизни TTL, или очередь переполняется):
    - RabbitMQ автоматически забирает это сообщение.
    - Пересылает его в указанный `DLX-обменник`.
    - Из `DLX` сообщение попадает в очередь брака — **DLQ (Dead Letter Queue)**.
3.  Сообщения лежат в `DLQ` и не мешают работе основной системы. Разработчик может зайти в админку, изучить тело ошибочного сообщения, исправить баг и запустить обработку заново.

### 7.2 Пример реализации `auth.consumer.ts`:

````typescript
import { Injectable, UseGuards } from '@nestjs/common';
import { AuthService } from './auth.service';
import {
  RabbitRPC,
  RMQ_EXCHANGES,
  RMQ_ROUTING_KEYS,
  RMQ_QUEUES,
} from '@app/common';

@Injectable()
export class AuthConsumer {
  constructor(private readonly authService: AuthService) {}

  @RabbitRPC({
    exchange: RMQ_EXCHANGES.DEFAULT,
    routingKey: RMQ_ROUTING_KEYS.AUTH.AUTHENTICATE,
    queue: RMQ_QUEUES.AUTH,
  })
  async authenticate(data: any) {
    return this.authService.validateUserInternal(data.userId);
  }
}

### ⚠️ Опасность: Смена типа существующего обменника

Если в RabbitMQ уже создан обменник `my-exchange` с типом `direct`, и ты попытаешься переопределить его в коде как `topic`, брокер выбросит критическую ошибку:

```text
PRECONDITION_FAILED - cannot redeclare exchange 'my-exchange' in vhost '/' with different type
````

## 9. Стратегии доставки сообщений (Delivery Guarantees) — Шпаргалка для собеседований

В распределенных системах гарантировать доставку сложно из-за сетевых сбоев, падений подов и перезагрузок брокеров. Физически по ненадежной сети невозможно передать сообщение ровно один раз без риска потери или дублирования (теорема "Проблема двух генералов"). Существует три режима гарантий:

### 9.1 At-Most-Once (Максимум один раз / "Отправил и забыл")

Самый быстрый, но наименее надежный режим. Сообщения могут теряться, но никогда не продублируются.

- **Как достигается:**
  - Отправитель шлет сообщения с `deliveryMode: 1` (Transient / только в RAM).
  - Очереди создаются с `durable: false` (не сохраняются на диск при перезагрузке RabbitMQ).
  - Потребитель подтверждает получение автоматически (`autoAck: true` / в момент считывания из сокета). Если воркер упадет в процессе выполнения функции, сообщение потеряно.
- **Где применяется:** Метрики, кликстрим, GPS-трекинг, сбор логов (где потеря 0.01% пакетов не критична).

---

### 9.2 At-Least-Once (Минимум один раз) — Стандарт для финансовых транзакций

Сообщения гарантированно дойдут, но при сбоях сети **возможны дубликаты**.

- **Как достигается:**
  - **Publisher Confirms:** Брокер отправляет сетевой ACK отправителю только после того, как сообщение сохранено.
  - **Durable Queues:** Очереди создаются с флагом `durable: true` (структура ящика переживет рестарт).
  - **Persistent Messages:** Сообщения публикуются с `deliveryMode: 2` (байты тела пишутся на SSD).
  - **Manual Consumer Acknowledgements:** `autoAck: false`. Потребитель отправляет `ack` только тогда, когда транзакция в базе данных успешно закоммичена. Если воркер упадет посередине, RabbitMQ вернет сообщение в очередь (requeue) и выставит системный флаг **`redelivered: true`**.

> ⚠️ **ГЛАВНАЯ ЛОВУШКА НА СОБЕСЕДОВАНИЯХ: Очередь vs Сообщения**
> Флаг `durable: true` на очереди сохраняет только **сам почтовый ящик**! Если отправить сообщение без `deliveryMode: 2` (Persistent), при перезагрузке RabbitMQ ящик останется на месте, но станет **абсолютно пустым** (сообщения сгорят). Для 100% защиты от потери данных нужны **ОБА** условия: `durable: true` на очереди И `deliveryMode: 2` у сообщения!

---

### 9.3 Exactly-Once (Ровно один раз)

Математически чистый Exactly-Once на уровне транспортного протокола в ненадежной сети невозможен. Если брокер записал сообщение и отправил ACK, но сеть моргнула и ACK не дошел до отправителя, отправитель пошлет сообщение заново.

- **Как достигается на практике (Паттерн Idempotent Consumer):**
  - Транспорт работает в надежном режиме **At-Least-Once** (сообщения не теряются, но могут дублироваться).
  - Продюсер прикрепляет уникальный идентификатор: заголовок `x-idempotency-key` (или ID заказа).
  - На стороне консьюмера реализуется **дедупликация**: перед выполнением бизнес-логики ключ проверяется в быстром атомарном хранилище (Redis `SETNX` с TTL или уникальный индекс в Postgres).
  - Если ключ уже существует — консьюмер блокирует повторное списание средств и мирно отправляет `ACK` (удаляет дубликат из очереди).

## 10. Идемпотентность и борьба с дубликатами

Идемпотентность — это свойство системы при многократном выполнении одной и той же операции возвращать один и тот же результат без побочных эффектов.

### 10.1 Источники дубликатов в RabbitMQ

1. **Дубликат при отправке (Sender Duplicate):** Продюсер отправил сообщение, брокер сохранил его, но сеть упала до отправки подтверждения продюсеру. Продюсер делает ретрай.
2. **Дубликат при обработке (Receiver Duplicate):** Потребитель считал сообщение, обработал его, сохранил в базу, но упал до того, как успел отправить `ack` в RabbitMQ. Брокер зафиксировал обрыв связи и вернул сообщение в очередь.

### 10.2 Стратегии дедупликации

#### 1. Уникальные идентификаторы сообщений (Message IDs)

Каждому сообщению при генерации присваивается уникальный UUID (например, в заголовке `messageId` или `x-message-id`).

- На стороне получателя используется распределенное хранилище (например, Redis) с операцией `SETNX` (set if not exists) с TTL (например, 24 часа):
  ```typescript
  const lockKey = `msg:lock:${messageId}`;
  const isUnique = await redis.set(lockKey, 'processing', 'NX', 'EX', 86400);
  if (!isUnique) {
    return ack();
  }
  ```

#### 2. Дедупликация на уровне БД (Unique Constraints)

Если операция — это создание записи, используем уникальный составной ключ в СУБД (например, `transaction_id`). Вторая попытка вставить запись упадет с ошибкой нарушения уникальности (Unique Constraint Violation), которую мы ловим в коде и просто подтверждаем сообщение.

#### 3. Паттерн "Outbox" (Transactional Outbox)

Чтобы избежать ситуации, когда запись в БД прошла успешно, а отправка события в RabbitMQ упала (или наоборот), используется паттерн Outbox:

1. В рамках одной транзакции СУБД сохраняется бизнес-сущность (например, заказ) и запись о событии в специальную таблицу `outbox`.
2. Отдельный фоновый процесс (через Change Data Capture типа Debezium или простой опросник) считывает таблицу `outbox`, отправляет события в RabbitMQ и отмечает их как отправленные.

## 11. Prefetch Count (QoS) и поведение под нагрузкой

Если запустить тяжелый микросервис и не настроить лимиты, RabbitMQ попытается вытолкнуть из буфера сокета **все** накопившиеся в очереди сообщения в этот воркер. Воркер захлебнется, память переполнится (Out of Memory), под упадет.

### 11.1 Prefetch Count (Quality of Service - QoS)

Prefetch Count задает лимит: **сколько максимум сообщений в статусе `Unacknowledged` может находиться на одном канале (или консьюмере) одновременно.**

- **Prefetch = 1:** Воркер берет ровно одно сообщение. Пока код не вызовет `ack()` или `nack()`, RabbitMQ не пришлет ему следующее. Это безопасно, но медленно (увеличивает простой воркера на сетевой пинг).
- **Prefetch = 10-50 (Оптимально):** Воркер буферизирует пачку сообщений. Пока он обрабатывает первое, следующие уже лежат в памяти процесса.
- **Prefetch = 0 (Без лимита):** Опасно. Приводит к падению воркеров под нагрузкой.

### 11.2 Поведение RabbitMQ под высокой нагрузкой (Flow Control)

Когда у брокера заканчивается оперативная память (Memory Alarm) или место на диске (Disk Alarm):

1. RabbitMQ переходит в статус **Blocking** или **Blocked**.
2. Он **перестает читать данные из TCP-сокетов продюсеров**.
3. Сетевые буферы продюсеров переполняются, и отправка сообщений из вашего кода начинает зависать по таймауту. При этом консьюмеры продолжают читать сообщения (брокер пытается освободить память).

## 12. Бесконечные циклы ретраев и счета в Datadog/ELK

Это одна из самых частых аварий в продакшне при переходе на очереди.

### 12.1 Сценарий катастрофы

1. Разработчик вешает гвард или валидацию на queue.
2. Прилетает сообщение, не проходящее валидацию.
3. Код выбрасывает `ValidationError`.
4. Фреймворк или библиотека автоматически делает `nack(requeue: true)` (пытается повторить).
5. Сообщение мгновенно возвращается в голову очереди.
6. Воркер берет его снова через 0.1 миллисекунды.
7. Ошибка пишется в консоль.
8. **Результат:** 10,000 логов об ошибке в секунду. Процессор ноды загружен на 100%. Агент Datadog отправляет миллионы строк логов в облако.
9. **Финал:** За выходные набегает счет в Datadog на $15,000.

### 12.2 Как защитить логи и кошелек

1. **Никогда не ретраить фатальные ошибки:** Ошибки валидации (Bad Request), парсинга JSON должны перехватываться в глобальном `Filter` или блоке `try-catch` и отправляться в `nack(requeue: false)` (в DLQ) сразу.
2. **Ограничивать количество ретраев (Retry Count):**
   При повторной отправке сообщения в заголовки (`headers`) нужно записывать счетчик попыток: `x-retry-count`.

   ```typescript
   const headers = msg.properties.headers || {};
   const retryCount = (headers['x-retry-count'] || 0) + 1;

   if (retryCount > 5) {
     channel.reject(msg, false);
   } else {
     publishToDelayQueue(msg, retryCount);
     channel.ack(msg);
   }
   ```

3. **Агрегация и троттлинг логов:** На уровне агента логирования (FluentBit, Datadog Agent) настраивать правила дедупликации повторяющихся ошибок.

## 13. Масштабирование и кластеризация (Classic, Quorum, Streams)

### 13.1 Classic Queues (Классические очереди)

Хранятся на одном конкретном узле кластера.

- В старых версиях поддерживали зеркалирование (Mirrored Queues), но этот режим объявлен **deprecated в RabbitMQ 4.0** из-за низкой производительности и проблем с синхронизацией при сетевых разделениях (Split-brain).

### 13.2 Quorum Queues (Кворумные очереди)

Современный стандарт для высоконадежных систем.

- Базируются на алгоритме консенсуса **Raft** (аналогично etcd или Consul).
- Очередь состоит из одного лидера (Leader) и нескольких последователей (Followers), распределенных по разным нодам кластера.
- Запись считается успешной, только если она подтверждена большинством (кворумом) узлов.
- При падении лидера выборы нового происходят за доли секунды.
- Кворумные очереди устойчивы к сетевым сбоям, но создают повышенную нагрузку на диск.

### 13.3 RabbitMQ Streams (Потоки)

Появились в RabbitMQ 3.9 как прямой конкурент Apache Kafka.

- **Это персистентный append-only лог сообщений на диске.**
- В отличие от классических очередей, сообщения из Stream **не удаляются после прочтения**.
- Позволяет множеству разных консьюмеров читать одни и те же данные с разной скоростью, перематывая указатель чтения (Offset) назад во времени.
- Обладает колоссальной пропускной способностью (миллионы сообщений в секунду), так как использует последовательную запись на диск и технологию OS page cache.
