## 1. Кворумные очереди (Quorum Queues) — Защита от падения серверов

### В чем проблема классической очереди (Classic Queue)?

Классическая очередь создается **на одном сервере**. Если этот сервер физически сгорает или у него ломается диск — все сообщения, которые лежали в очереди, **исчезают навсегда**.

### Как решают Кворумные очереди (Quorum Queues):

Кворумная очередь — это очередь, которая **автоматически реплицируется (копируется) на 3 сервера** по алгоритму консенсуса **Raft**:

```text
               ┌────────────────────────────────────────────────────────┐
               │              КВОРУМНАЯ ОЧЕРЕДЬ (3 СЕРВЕРА)             │
               │                                                        │
               │  [ Сервер 1 ]            [ Сервер 2 ]    [ Сервер 3 ]  │
               │ ┌──────────────┐        ┌──────────────┐┌─────────────┐│
               │ │    ЛИДЕР     │───────►│   ФОЛОВЕР    ││   ФОЛОВЕР   ││
               │ │  (Принимает  │(Копия) │   (Копия)    ││   (Копия)   ││
               │ │   запись)    │        │              ││             ││
               │ └──────▲───────┘        └──────────────┘└─────────────┘│
               └────────┼───────────────────────────────────────────────┘
                        │
                [ Продюсер NestJS ]
```

1. **Как работает запись:** Продюсер отправляет заказ. Лидер записывает его себе на SSD и отправляет копии на Сервер 2 и 3. Как только хотя бы один сервер подтвердил копирование (**Кворум = 2 из 3**) ➔ продюсеру возвращается успех.
2. **Что если Сервер 1 сгорит прямо сейчас?**
   Сервер 2 и 3 за **0.2 секунды** выбирают нового Лидера. Ни одно сообщение **НЕ теряется**, сайт продолжает работать без остановки!

### Как включить кворумную очередь в NestJS (Всего 1 строчка!):

```typescript
@RabbitRPC({
  exchange: 'default-exchange',
  routingKey: 'create_payment_quorum',
  queue: 'payments.quorum',
  // 👇 ВОТ ВСЯ НАСТРОЙКА: говорим брокеру создать Quorum Queue с репликацией:
  queueOptions: {
    arguments: {
      'x-queue-type': 'quorum', // 👈 Кворумная очередь с консенсусом Raft!
      'x-delivery-limit': 5,    // 👈 Автоматический сброс в DLQ после 5 неудач
    },
  },
})
async handleQuorumPayment(data: any) { ... }
```

## 2. Шардирование очередей (Queue Sharding) — Разгон до 100k+ msg/s

### В чем проблема одной очереди при огромной нагрузке?

Одна очередь в RabbitMQ обрабатывается **одним ядром процессора**.  
Если на распродаже летит **100 000 заказов в секунду**, одно ядро физически упирается в 100% CPU и начинает тормозить.

### Как решает Шардирование (Consistent Hash Exchange):

Мы создаем **не одну очередь, а 3 параллельных шарда (суб-очереди)**, которые живут на разных серверах и на разных ядрах CPU:

```text
                              [ sharded-orders-exchange ]
                              (Тип: x-consistent-hash)
                              /            |             \
                       (Хэш 0..33)    (Хэш 34..66)   (Хэш 67..100)
                           ▼               ▼               ▼
                     [ shard-1 ]      [ shard-2 ]     [ shard-3 ]
                      (Ядро 1)         (Ядро 2)        (Ядро 3)
```

## 3. Разбор главного заблуждения: почему в коде нет жестких привязок

> ❌ **Миф:** «Продюсер должен знать, в какой шард `shard-1` или `shard-2` слать, и это жесткая привязка к серверу».

### ✅ Реальность: Продюсер шлет в ОДИН ОБЩИЙ ОБМЕННИК!

Посмотри на реальный код продюсера:

```typescript
// В ReservationService:
async createReservation(userId: number, amount: number) {

  await this.amqpConnection.publish(
    'sharded-orders-exchange', // 👈 1. Общий обменник (про шарды продюсер НЕ ЗНАЕТ!)
    String(userId),            // 👈 2. Просто ID пользователя как строка ('user-42')
    { amount, sentAt: new Date() },
  );
}
```

вот тут не понятно почему мы в роутинг ключ запихиваем пользователя ведь раньше мы делали

@Post('test/direct')
async testDirect(@Body() body: { message: string }) {
await this.amqpConnection.publish(
RMQ_EXCHANGES.DIRECT_TEST,
RMQ_ROUTING_KEYS.DIRECT_TEST,
{ text: body.message, sentAt: new Date() },
);
return { success: true, mode: 'direct', message: body.message };
}

### Как брокер САМ распределяет сообщения:

1. Продюсер передал `userId: "42"`.
2. Обменник `sharded-orders-exchange` внутри RabbitMQ берет строку `"42"` и вычисляет математический хэш.
3. Брокер **САМ решает**, в какой шард положить сообщение:
   - Все заказы пользователя `"42"` брокер всегда положит в `shard-2` (сохраняя порядок FIFO для этого юзера).
   - Заказы пользователя `"99"` брокер положит в `shard-1`.
   - Заказы пользователя `"105"` брокер положит в `shard-3`.

**Продюсер вообще не знает, сколько шардов создано (3, 10 или 50) — он просто шлет в один обменник!**

## 4. Типы обменников в RabbitMQ (Почему именно `x-consistent-hash`?)

По стандарту протокола **AMQP 0-9-1** все обменники, расширяющие базовые возможности через плагины, начинаются с префикса **`x-`** (_eXtended_).

### Стандартные типы vs `x-` типы:

| Тип обменника           | Принцип работы                                      | Назначение                                  |
| :---------------------- | :-------------------------------------------------- | :------------------------------------------ |
| `direct`                | Точное совпадение ключа (`key === 'create_charge'`) | Точечная отправка конкретной команде        |
| `fanout`                | Вещание во все привязанные очереди (Broadcast)      | События на весь кластер (`UserRegistered`)  |
| `topic`                 | Фильтрация по маске (`eu.*.orders`, `logs.#`)       | Иерархическая маршрутизация                 |
| `headers`               | Фильтрация по полям в объекте заголовков `headers`  | Сложные фильтры по атрибутам                |
| **`x-consistent-hash`** | **Хэш-кольцо (Hash Ring) от ключа (`userId`)**      | **Шардирование очередей и масштабирование** |
| `x-delayed-message`     | Задержка доставки на $N$ миллисекунд                | Нативные отложенные задачи (Delayed Tasks)  |
| `x-random`              | Случайный выбор одной из очередей                   | Равномерная случайная балансировка          |

## 5. Сравнительная шпаргалка для архитектора

| Задача                                                       | Решение                        | Что пишем в коде?                                                         |
| :----------------------------------------------------------- | :----------------------------- | :------------------------------------------------------------------------ |
| **«Нужно, чтобы при сгорании ноды платежи не пропали»**      | **Quorum Queues**              | `'x-queue-type': 'quorum'` в настройках очереди                           |
| **«Нужно переварить 100 000 msg/s на многоядерном сервере»** | **Sharding (Consistent Hash)** | `type: 'x-consistent-hash'` + `publish('exchange', String(userId), data)` |
| **«Нужно гарантировать коммит в БД и отправку в брокер»**    | **Transactional Outbox**       | `outboxService.create(entity, event)` со `SKIP LOCKED`                    |
| **«Нужно задержать сообщение на 15 минут»**                  | **Delayed Message Exchange**   | `type: 'x-delayed-message'` + заголовок `x-delay: 900000`                 |
